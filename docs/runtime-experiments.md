# M0 实机能力验证清单

本清单对应[开发设计文档](development-design.md) §13.1。代码中的 136 个自动化测试只覆盖逻辑与构建产物；下列行为依赖 iOS、Surge 和 Bilibili App 的真实运行时，必须在目标设备上逐项确认。每项都记录 iOS、Surge、Bilibili App 版本及网络类型。

## 手机首轮验证

先在 Wi-Fi 下验证手动流程，再测试自动模式。远程安装地址见 [README](../README.md#安装)。本轮使用 v0.4.0 固定脚本，避免测试期间随主分支源码变化。

### 安装与初始参数

1. 备份当前 Surge 配置，暂时停用 Biliverse Redirect 及其他匹配相同视频请求的 CDN 改写规则。
2. 在 Surge 的模块管理中选择通过 URL 安装，粘贴远程模块链接，启用 Bilibili CDN Picker。检查脚本资源下载没有失败或 404。
3. 参数设置为 `ENABLED=true`、`MODE=manual`、`REGION=SG`、`HISTORY_POLICY=conservative`、`CELLULAR_DISCOVERY=false`、`DEBUG=true`；`TARGET_MBPS` 保持 80，`PROBE_POLICY` 初次留空。
4. 开启 Surge 的 MITM 和脚本功能。已有可用的 Surge CA 时复用它；否则在 Surge MITM 设置中生成并安装证书，按 iOS 引导完成描述文件安装，再到“设置 → 通用 → 关于本机 → 证书信任设置”开启该 Surge CA 的完全信任。模块追加本机控制台域名 bcp.test 和媒体域名，不需要设置全域通配。参见 [Surge MITM](https://manual.nssurge.com/http/mitm.html) 和 [Apple 证书信任说明](https://support.apple.com/zh-cn/102390)。

## v0.4.0 网页实机验收

1. 更新当前使用的原版或诊断版模块（安装来源须为 `/main/` 地址），不要同时启用两版。确认外部资源里 `web-control.js` 可下载；诊断版静态标记应为 v0.4.0。
2. 保持 Surge 开启、MITM CA 已信任，Safari 打开 [CDN Picker](https://bcp.test/)。应出现 v0.4.0 和“Surge 已连接”，不能出现“模拟网络”（那是电脑开发预览）。确认地址仍是 `bcp.test`，没有跳转到公网服务。
3. 若打不开，查看 Surge 中 `bcp.test` 请求：生效配置应有精确 MITM 主机、`[Host] bcp.test = 127.0.0.1` 和 `BiliCDN-Web` 请求脚本。同一请求只执行第一个匹配脚本，检查通配脚本是否抢先命中；不要关闭证书验证。脚本报错或内存提示时记录具体脚本名。Home → Modify → Scripting 是否列出模块脚本不作为加载判据。
4. 网页能打开后，先观察空闲状态约 15 秒：允许 `/api/status` 请求，不应新增 CDN Range 探测。这确认轮询没有偷偷启动测速。
5. B 站播放普通 UGC 视频，固定 1080P 或 4K 约 10 秒，然后两分钟内返回网页。选“视频”，确认资源编号和样本时间，再点击“优化当前视频”。保持网页前台，观察粗筛→复筛→确认。另开同源页面应能查看进度，不应重复启动任务。
6. 完成后区分三种结果：“已选择视频线路”表示已确认替代节点；“原生线路已达到目标／保留当前原生线路”表示确认后无须切换；“尚未确认”表示没有可用于本资源的确认决策。音频选项的确认不能让未测视频显示成功。
7. 观察结果表：粗筛／复筛是“待确认”；只有通过确认的节点为“已确认”。未覆盖全量时必须显示部分探索，流量中的不可观测预留不能伪装成精确实测流量。
8. 返回同一个视频、同一画质，拖到未缓冲处。在 Surge 查看新请求：若选择了替代节点，URL 主机与 Host 应匹配网页选择，路径和 query 不因本模块改变；通常响应 206。保持原生时不要求主机变化。结束测速再比较缓冲次数、拖动恢复时间，测速过程中带宽竞争不计为优化收益。
9. 若需验证完整探索，在 Wi-Fi 点击“探索更多节点”并确认 100 MiB 目标预算。默认约 60 秒内结束；粗筛可能约半程转复筛以保留确认时间，部分覆盖是诚实结果。中途点击停止后，应不再派发新的探测，在途请求结束才退出忙碌；再启动一次任务应可成功。
10. 设置中修改目标速率（如 80→90），保存并刷新确认保留，再恢复原值。暂停改写后应显示原生路径，恢复后才使用有效选择。任务运行时设置保存及清空历史按钮应禁用。
11. Safari 分享 → 添加到主屏幕。关闭页面，从桌面图标重新打开，应该连接同一份本机状态。关闭 Surge 后无法连接属于预期；重新开启后恢复。任务期间保持前台，不将切后台／锁屏后的持续执行视为已保证能力。
12. 出现问题时记录页面版本、当前视频／音频、任务阶段、已测数量、停止原因、Surge 错误中的脚本名和网络类型；分享截图前隐藏完整签名 URL 与请求凭据。

### 缓存、自动模式与面板

网页对已确认资源显示“重新测速”，该按钮明确使用 `quick-force`，会重新下载；仅刷新页面、切换视频／音频标签和打开只读面板不会测速。旧快捷指令 `quick` 遇到有效决策仍返回缓存命中。自动模式默认关闭，手动和任务生命周期通过后再单独测试 `MODE=adaptive`。

v0.4.0 的 Surge 面板是只读网页入口，诊断版另保留静态安装标记。若更新后还有完整探索／停止面板，核对旧版或重复模块是否仍启用。不要通过更改 Bilibili 的 DIRECT 策略寻找面板；DIRECT 是出口方式，与模块是否可拦截请求是两回事。

## 准备

1. 备份 Surge 配置，停用 Biliverse Redirect 等会改写同类媒体 URL 的模块或脚本。
2. 安装模块（见 [README](../README.md#安装)），模块参数设 `DEBUG=true`，确认 MITM 证书已信任。
3. 在 Surge 的请求查看器中筛选 `bilivideo`、`akamaized`；脚本日志可在 Surge 的脚本日志页查看；DEBUG 同时开启原生请求备注输出，所有行以 `[BiliCDN]` 开头。
4. 持久化数据键名均以 `BiliCDNPicker.` 开头，可在 Surge 的脚本数据查看器中检查。

## 实验与判定

| 实验 | 操作 | 通过证据 | 未通过时 |
| --- | --- | --- | --- |
| 媒体请求识别 | 播放一个 UGC 视频 20 秒 | 请求记录中 `/upgcxcode/…m4s` 的请求带 `BiliCDN-Router` 脚本标记；`BiliCDNPicker.samples` 出现视频与音频样本；其他 B 站接口无标记 | 把实际 URL 族加入新适配器前保持直通，不放宽 pattern |
| Host 与 URL 改写 | 网页启动快速选择后继续播放 | 请求记录显示新主机，`Host` 与 URL 主机一致，路径与 query 未变；响应为 206 | 用快捷指令参数 `pause` 暂停改写或停用模块，保存失败请求记录后再修正适配器 |
| Range 行为 | 查看测速请求（请求头含 `X-BCP-Probe`） | 状态 206、`Content-Range` 与请求区间一致；网页流量行无“超出 Range”计数 | 对出现 200 或错位区间的节点记录型号与时段，确认冷却生效 |
| timeout 精度 | 在 `BiliCDNPicker.config` 写入 `{"coarseTimeoutMs":300}` 后点按，再恢复 | 超时请求在约 0.3 秒处结束，而非 1 秒或 5 秒 | 把 `coarseMinTimeoutMs` 调到实测最小精度 |
| 并发上限 | 完整探索时观察请求记录 | iOS 上同时进行的测速请求不超过 2，复筛和确认串行，任务能结束 | 降低 `discoveryConcurrency` |
| 独立任务生命周期 | `MODE=adaptive` 后播放新视频 | 面板“自动触发”时间更新，随后 `BiliCDNPicker.lastRun` 的 `trigger` 与结果更新，同一视频后续请求被改写 | 保持 `MODE=manual`，仅用网页或快捷指令触发 |
| 脚本递归 | 运行一次快速选择 | 日志中没有 `probe re-entered`；若有，确认测速请求离开设备前已去掉 `X-BCP-Probe` 且未被改写 | 若标记头外泄且服务端拒绝，设置 `probeMarker:false` 并重新评估 |
| 出口一致性 | 分别在 DIRECT 与代理策略下播放并测速 | 请求记录中测速与播放走同一策略；更换出口后修改 `ROUTE_REVISION` 会形成新的网络画像 | 设置 `PROBE_POLICY` 为播放实际使用的策略 |
| 网络切换 | 完整探索进行中切换 Wi-Fi 或蜂窝 | `lastRun` 中出现 `commit_rejected` 或停止原因“网络已变化”，新网络没有旧决策 | 保持手动模式，禁止跨切换提交 |
| 任务互斥 | 完整探索进行中再点按快速选择 | 面板显示“已有任务在运行”，没有重叠的测速请求 | 只保留一个手动入口 |
| 响应观察归属 | 选出 winner 后，临时用 Surge Map Local 让该主机的 `/upgcxcode/` 请求返回 403，继续播放；结束后删除该规则 | 请求与响应具有相同 `$request.id`，`BiliCDNPicker.request.*` 有该请求的实际目标及原网络；`failures.networks[networkKey]` 只记录对应目标，后续请求退回已确认备选或原生 | ID 缺失、关联槽过期或不匹配时应跳过观察；不得恢复当前路由推断。Map Local 若先于脚本匹配而无法复现，等待自然失败样本 |

## 审查修复的实机补充验证

- 播放原生请求尚在进行时选出新节点；原生请求随后失败，只记录原生失败，不将新 winner 加入失败表。
- 测速标记在请求脚本中被删除后，其响应仍通过请求 ID 被识别为 probe，不产生播放失败记录。
- Wi-Fi 请求仍在进行时切到蜂窝；旧响应产生的失败只出现在旧网络的 `failures.networks` 中。
- 所有已确认目标失效后，网页快速选择可以重测；自动模式须等待 `retryAfterFailureSeconds`（默认 300 秒）并取得新鲜样本，不能每次请求都启动扫描。
- 热路径现在额外写入有界请求关联槽，必须重新测量附加延迟。模拟测试结果不能替代这一项。

## 附加延迟测量

发布门槛要求热路径 P95 不超过 100 ms。关闭与开启模块各播放同一视频 5 分钟，比较请求记录中媒体请求的脚本耗时；样本少于 50 个时不下结论。

## v0.3.2 复测重点

- 截图对应的 HTTPS Akamai 音频 30232、视频 30066 路径在匹配测试中通过；协议或端口不符时不改写。
- HTTP Akamai 请求的默认端口及显式 `:80` 都可采样，探测和真实改写保持原协议及签名。HTTP 与 HTTPS 的决策键隔离。
- 开启 DEBUG，产生新的媒体请求，检查 `router_matched` 和 `sample_captured`。前者每次匹配均输出，后者受样本写入节流限制。
- 无面板时可用快捷指令选择已配置的诊断脚本；主配置 Scripting 编辑列表为空不构成故障证据。只读诊断不会触发测速流量。
- 若连静态安装标记和脚本都不存在，收集当前配置名称、模块来源和状态；避免发送完整配置中的代理凭据及证书私钥。


## v0.3.3 内存优化复测（历史入口，v0.4.0 按上方网页步骤执行）

1. 确认安装来源包含 `/main/`，更新模块后看到 `CDN Picker v0.3.3`；带提交 SHA 的旧来源需换成固定地址一次。
2. 先点快速选择一次，观察任务阶段、已完成／已启动数量和租约倒计时。任务未结束时再次点击应只显示忙碌，不创建重复扫描。
3. 需要中止时点“停止测速”面板；它停止派发并等待在途回调，不立即取消底层下载。进程若被系统终止，旧锁须等到期，下一次运行才能接管，默认最长约 75 秒。
4. 快速选择无异常后，再在 Wi-Fi 上测试完整探索。采样大小仍为 128 KiB、1 MiB 和 4 MiB，Top 20／5 和 100 MiB 预算未改变；粗筛最多 2 并发，其他阶段串行，可能更早触及时限并输出部分探索。
5. 若再次出现内存告警，记录告警中的脚本名、面板阶段、已完成数量，以及是否有不遵守 Range 的 200 响应；不要反复启动扫描。当前修复降低正文持有和并发，不保证单个异常响应的 native 内存峰值可控。

# Bilibili CDN Picker 开发设计文档

版本：0.3.2 开发设计（实现状态与审查修复见 §18）

整理日期：2026-10-14  
目标环境：新加坡网络下的 iOS Bilibili App 与 Surge  
项目目录：`bilibili-cdn-picker`

Bilibili CDN Picker 根据当前视频资源的实际下载表现，选择适合当前网络的 CDN，并在后续媒体请求中使用该节点。默认先将地区推荐、本机历史与少量探索节点合成为不超过 20 个候选，再进行分阶段 Range 测速、滚动调度和满足播放需求后的提前停止。全域清单用于逐步扩展与手动完整探索。

核心决策是：**不按地理距离排除候选，不在每个视频开始时完整扫描所有节点，不把一次小文件下载的冠军视为永久最佳节点。** 日常模式寻找足够快且可用的节点；完整探索模式负责发现历史候选之外的好线路。

本文整理自 [ChatGPT 分享对话](https://chatgpt.com/share/6acf432d-c9ac-83ec-82e4-b3eafbdb45c3)，并补充了工程设计与接口核对。对话完整存档见 [原始问答](sources/shared-chat.md)，机器可读版本见 [JSON 存档](sources/shared-chat.json)。原对话中的体验描述属于用户观察，示意测速数字不作为性能基准。下文的参数、数据模型和验收指标为实现规格。v0.3.2 已交付可导入的 Surge 模块（手动探索版），实机能力验证尚未完成，实现状态与设计取舍见 §18。

## 1 背景与需求演进

### 1.1 原始问题

用户在新加坡使用 B 站网页版时，遇到视频画面停止但音频继续的现象。讨论随后转向手机端，并明确用户已使用 Surge，希望在手机上自动测速和选择 CDN，减少手动切换。

排障必须区分两个方向：视频数据未及时到达，以及解码或渲染未正常推进。音频仍在播放不能单独排除网络问题；视频缓冲充足也不能单独证明某个浏览器缺陷。CDN Picker 只处理媒体请求路径和下载表现，不承担解码器、GPU、浏览器全屏合成等问题的修复。

### 1.2 五轮对话的落地结论

| 轮次 | 对话主题 | 对项目的影响 |
| --- | --- | --- |
| 1 | 网页卡顿与音画不同步诊断 | 将网络问题与播放器问题分开，建立可观测的对照实验 |
| 2 | 手机端方案 | 使用网络层 CDN 改写作为主要方向，手动固定节点作为基线 |
| 3 | Surge 自动测速与选择 | 采集真实媒体 URL，Range 下载，对结果按网络缓存 |
| 4 | 武汉节点实测快于香港节点 | 放弃仅测试附近 6～10 个节点的限制，支持全域发现 |
| 5 | 快节点很早完成 | 改用滚动 worker、短探测、分阶段确认和提前停止 |

用户实际观察是武汉 CDN 当时最快，香港节点只有很低的下载速度。这说明候选选择不能仅凭城市距离；不等于武汉在所有运营商、视频和时段都更快。原文未提供获胜武汉节点的完整 hostname，开发时不能凭城市名称补造地址。

### 1.3 参考方案与定位

网页侧的 [bilibili-cdn-switcher](https://github.com/a0972199950/bilibili-cdn-switcher) 提供节点选择、测速和失败切换，可作为候选数据与实验方法的参考。节点总量会变化，设计中的“300”只是容量和流量计算样本，实际处理数量取自去重后的清单。

手机侧的 [Biliverse Redirect](https://biliverse.github.io/guide/redirect.html) 提供视频源主机名改写和 Host 配置。项目借鉴其改写目标，但自动发现、测速与选择由本项目负责。原对话提到的扩展商店评分、用户数及“最新版本”不属于实现依赖。

## 2 目标与范围

### 2.1 功能目标

| 编号 | 需求 | 验收方向 |
| --- | --- | --- |
| R01 | 从真实播放请求提取可测试媒体资源 | 保留原路径、查询字符串及必要请求上下文 |
| R02 | 支持数百个候选节点 | 无硬编码的 300 节点上限，不按国家筛掉节点 |
| R03 | 分阶段测量 | 小 Range 粗筛、中等 Range 复筛、大 Range 确认 |
| R04 | 滚动并发 | 任一请求结束立即释放 worker，无整批等待屏障 |
| R05 | 提前结束搜索 | 达到确认阈值后停止派发，并正确处理在途请求 |
| R06 | 按网络复用结果 | Wi-Fi、蜂窝和代理出口上下文隔离 |
| R07 | 避免拖慢播放 | 请求路径只做轻量决策，不等待全量探索 |
| R08 | 失败降级 | 备选节点或原始 URL，限制重试和反复切换 |
| R09 | 控制流量 | 配置化预算，蜂窝默认禁止自动全量探索 |
| R10 | 可诊断与可关闭 | 展示选择原因、覆盖率、测速开销及失败类型 |

### 2.2 首期范围

当前支持 HTTP 80 和 HTTPS 443 的点播媒体请求，资源族仍严格限定为 `/upgcxcode/…m4s`，优先覆盖中国大陆版 Bilibili App 的常见视频与音频资源。针对每一类 URL 建立适配器和测试样本，再逐步扩大匹配范围。

直播、BStar 国际版、特殊 PCDN/MCDN 路径转换、DRM 或区域授权处理、账号能力变更以及 Android App 补丁均不属于首期。原对话提到的 Android、代理、DNS 和浏览器替代方案保留为背景与排障手段，不扩展成本项目必须实现的平台。

### 2.3 成功的定义

成功标准是播放首帧等待、缓冲次数和拖动恢复时间得到改善，同时额外流量可控。吞吐排行榜是选择工具，不能代替播放体验验收。有限采样和提前停止都不保证找到全局最优节点；界面只能称其为“本轮已测最佳”或“已满足目标”。

## 3 开发前必须固定的技术边界

### 3.1 Surge 已核对的基础能力

Surge 提供请求 URL 改写、二进制 HTTP 请求、持久化存储和网络环境字段。`$httpClient` 的 timeout 使用秒；每次脚本运行最多 20 个并发请求，iOS 请求和响应体有 32 MB 上限。它使用完成回调，公开接口未列出单请求取消句柄或下载进度回调。不要把此结论扩大成所有 Surge 引擎都不支持其他网络 API。见 [JavaScript API](https://manual.nssurge.com/scripting/api.html)。

HTTPS 请求须进入 Surge HTTP 处理流程，并对来源主机启用相应 MITM。请求脚本改 URL 时不会自动同步 Host；同一请求只执行第一条启用且匹配的请求脚本。见 [请求脚本说明](https://manual.nssurge.com/scripting/http-request.html)。

脚本本身有独立的执行超时，默认 5 秒；不能只设置单个 HTTP 请求的超时。JSC 与 WebView 还有各自的并行会话限制，因此一个长期测速任务可能影响其他脚本排队。见 [脚本运行说明](https://manual.nssurge.com/scripting/overview.html)。

### 3.2 对原方案的必要修正

| 原讨论中的简化表达 | 工程规格 |
| --- | --- |
| 先 `$done()` 放行，然后继续后台测速 | 必须使用独立的任务生命周期；不依赖已结束请求脚本继续执行 |
| 淘汰慢节点立即释放 worker | 无取消能力时只能逻辑淘汰，必须等真实回调后才释放占用 |
| 128 KiB 很快完成即可认定持续高速 | 粗筛成绩只表示这段采样的完成表现，需较大样本确认 |
| 滚动队列最先完成的 20 个就是 Top 20 | 按各自启动后的耗时比较；晚启动的节点仍有入围资格 |
| 收到 Range 请求就只消耗指定字节数 | 服务端可能忽略 Range；预算上限必须写明成立条件 |
| 一个赢家适用于全部视频 | 网络历史仅作先验，资源兼容性与当前视频结果单独缓存 |
| 请求脚本可直接发现真实播放超时 | 请求脚本尚未看到响应；需要响应观察或额外请求遥测 |
| 改写后必然在下个 segment 生效 | 只能影响后续新请求；长连接、预取和现有 Range 不会被回溯修改 |

这些修正保留原对话的优化目标，同时防止实现依赖不存在的时序和取消能力。

## 4 总体架构

### 4.1 组件划分

| 组件 | 职责 | 不应承担的工作 |
| --- | --- | --- |
| Request Router | 验证 URL、读取决策、改写 hostname、采集样本 | 不执行全量测速 |
| Sample Store | 暂存最新可用媒体请求上下文与过期信息 | 不永久保存签名 URL |
| Discovery Runner | 分阶段派发探测、计算结果、提交排行榜 | 不拦住播放请求等待全部结束 |
| Candidate Registry | 管理候选地址、来源、版本及适配类型 | 不把城市名当速度依据 |
| Network Context | 构造网络与出口上下文指纹 | 不假设 SSID 就唯一代表网络 |
| Decision Store | 保存网络排行、资源选择、冷却与任务状态 | 不提供并未实现的跨会话原子锁 |
| Response Observer | 记录可见响应状态，触发后续降级 | 不缓冲整段视频来测速 |
| Control Panel | 显示状态、请求探索、暂停、清缓存 | 不每次刷新都启动下载 |

```text
Bilibili 新媒体请求
        │
        ▼
Request Router ─── 读取资源决策与网络历史
        │
        ├── 无可用决策 ── 原请求放行
        └── 有效决策 ──── 仅改写目标地址及对应 Host
        │
        └── 更新短期 Sample Store 和待测标记
                                  │
                         独立 Discovery Runner
                                  │
                  候选清单 → 粗筛 → 复筛 → 确认
                                  │
                         Decision Store
                                  │
                    后续新请求读取新决策
```

### 4.2 后台任务的实施顺序

**MVP 使用手动触发的独立任务。** 请求脚本采集样本并立即放行；用户在面板或 Surge 脚本入口启动发现任务；任务结束后，后续请求读取缓存。这样可先验证测速和改写是否有效，无须在初版依赖跨脚本自动调度。

**自动版增加独立调度器。** 自动调度是下一阶段的实现任务：可评估受支持的脚本调用入口，或低频调度器检查待测标记。调用必须能够形成独立会话，并在请求脚本结束后继续完成和落盘；仅看到 API 返回成功不算验证通过。未通过生命周期实验时，自动功能保持关闭，保留手动入口。

若采用定时调度器，它只消费新鲜样本和待测标记。没有近期播放、没有合法样本或没有预算时不下载。原对话反对的是对旧签名 URL 无条件定时测速，并不妨碍用定时入口消费有效工作队列。

### 4.3 请求热路径

每次请求只执行以下顺序：

1. 验证方法、协议、来源主机和媒体资源类别。
2. 计算网络上下文与资源键；无法可靠识别时采用更保守的短期缓存。
3. 有当前资源的有效 winner 时使用；只有网络历史时按已验证兼容策略处理。
4. 没有可信目标、配置损坏或读取失败时，原请求放行。
5. 对样本存储进行节流更新，避免每个 Range 都写持久化存储。
6. 最终路径只调用一次 `$done`。

请求路由还按 `$request.id` 记录请求发出时的实际目标、原生主机、资源键、网络键、网络代次和决策身份，供响应观察关联；不保存完整签名 URL 或敏感请求头。

首期优先保证播放连续性。历史赢家未经当前资源验证时，默认保留原 URL，同时将该赢家排在下一次测试前列。是否允许直接使用历史赢家作为乐观加速，是后续可选项，需要有明确的资源适配范围和降级证据。

## 5 媒体 URL 与候选节点

### 5.1 候选清单

候选清单采用独立数据文件，至少包含 `hostname`、`family`、`source`、`enabled` 和清单版本。另维护按用户出口国家组织的地区推荐表，用作冷启动候选先验。CDN 机房所在地、厂商和 pool 可用于展示与探索多样性，不作为从全域清单永久删除节点的条件。

原对话中的样例包括：

```text
upos-sz-mirroraliov.bilivideo.com
upos-sz-mirrorcosov.bilivideo.com
upos-sz-mirrorhwov.bilivideo.com
upos-sz-mirrorawsov.bilivideo.com
cn-hk-eq-01-01.bilivideo.com
cn-hk-eq-01-09.bilivideo.com
cn-hk-eq-01-13.bilivideo.com
upos-sz-mirror08c.bilivideo.com
```

这些只是原方案样例，不能当作已通过连通性或兼容性检查的种子清单。清单应从明确来源导入、去重并校验；引用开源项目的数据或代码前确认许可证和保留署名要求。每轮都纳入当前视频原生分配的 CDN，作为对照和候选。`enabled:false` 对所有替换候选来源生效，包括地区表、历史、用户优先节点和缓存决策；同一主机的重复条目中，显式禁用优先。原生 CDN 仍保留为直通与对照，不因候选禁用而阻断 App 原始请求。

### 5.1.1 Chrome 扩展的地区预筛机制

2026-10-14 核对扩展源码提交 `210cacd1426ba2301ec647dd90bc8957b7634196`。实际流程为：查询 B 站 zone API 的出口国家字段，将返回的国际电话区码映射到 `countries[].dial`，再取对应 `countries[].nodes`。这是项目随版本发布的静态推荐表，不是客户端每次先扫描 299 个主机，也不是按 CDN 机房与用户之间的地理距离排序。该提交的全量 `options` 有 299 个实际 hostname，另有一个 `backup` 特殊项。见 [候选清单源码](https://github.com/a0972199950/bilibili-cdn-switcher/blob/210cacd1426ba2301ec647dd90bc8957b7634196/src/cdn-list.json)。

新加坡推荐表依次为：

| 2 | `upos-sz-mirrorhwo1.bilivideo.com` | 华为云 常规池 |
| 3 | `upos-sz-mirrorhw.bilivideo.com` | 华为云 常规池 |
| 4 | `upos-sz-mirrorali.bilivideo.com` | 阿里云 |
| 5 | `cn-jssz-cm-02-08.bilivideo.com` | B站 江苏苏州 移动 |
| 6 | `upos-sz-mirror08ct.bilivideo.com` | 华为云 常规池 |
| 7 | `cn-hk-eq-01-14.bilivideo.com` | B站 香港 |
| 8 | `cn-jxnc-cm-01-04.bilivideo.com` | B站 江西南昌 移动 |

因此，新加坡用户的推荐第一项已经是武汉节点。它可以作为冷启动先验，但不能据此认定就是用户上次实测获胜的同一个 hostname。清单注释强调 pool 分散，实际 SG 表包含多个相同华为 pool 的主机，并非严格一池一个。

`countryHosts()` 返回所选国家的列表；`ALL` 返回完整候选，但会清空自动测速列表并禁用对应开关。自定义列表另有入口。代码会默认选国家列表第一项，国家识别不命中时回落 TW；刷新出口信息不会自动覆盖用户已经选定的国家。见 [popup.js 的候选选择逻辑](https://github.com/a0972199950/bilibili-cdn-switcher/blob/210cacd1426ba2301ec647dd90bc8957b7634196/src/popup.js#L315-L474)。

该提交的 `FEATURE_AUTO_TEST_ON_COUNTRY` 在 popup 与主脚本中均为 false，因此不能沿用原对话“安装或切国家必定自动测速一次”的说法。独立的逐视频自动测速开关默认也关闭，开启后才走相应路径。测速按候选逐个执行，用流式读取和取消机制限制采样，默认 8 MiB 或 5 秒；这与 Surge 的固定 Range 完成回调模式不同。见 [main-hook.js 的测速实现](https://github.com/a0972199950/bilibili-cdn-switcher/blob/210cacd1426ba2301ec647dd90bc8957b7634196/src/main-hook.js#L1087-L1275)。

本项目借鉴地区推荐表作为候选先验，随后叠加当前网络实测。用户可直接设置地区为 SG，初版不必增加出口 IP 查询依赖；无法确认国家时使用本地历史、原生 CDN 和多样性探索，而非静默套用 TW。地区表需要版本化，不能将扩展推荐名单标成手机端已验证结果。

拒绝候选中的 scheme、路径、userinfo、控制字符和未允许端口，防止将“hostname 字段”误当成任意 URL。域名匹配必须有边界，例如不能把 `bilivideo.com.attacker.example` 识别成 B 站域名。

### 5.2 改写规则

对已验证的资源族，只替换 URL 的 authority 中的目标主机部分；保留原始 pathname 和 query 的字节表达，不重排参数，不重新编码 `%`、`+` 或重复参数。若旧 URL 包含非标准端口，必须由该资源族适配器决定是否支持；不能把 PCDN 的专用端口盲目带到另一台服务器。

同步处理 Host 请求头的大小写变体，避免同时存在旧的 `host` 和新的 `Host`。除明确需要修改的字段外保留播放请求语义；不能把测速用的 Range 覆盖到真实播放请求上。实际 HTTP/2 authority 和 TLS 目标的一致性要通过 Surge 请求记录验证。

跨主机签名不一定兼容。403 或 404 可能表示当前资源在该主机上不可访问，而非整个 CDN 永久失效。不同路径族之间不做通用替换猜测；尚未验证的路径原样放行。

### 5.3 资源一致性

同一轮必须测试同一个视频或音频 representation、同一字节区间和同一出口策略。不能拿节点 A 的低码率音频和节点 B 的高码率视频比较。

资源键至少区分协议、有效端口、媒体类型、路径、清晰度或 representation，以及必要的身份和有效期上下文。若暂时不能解析视频 ID，使用路径与相关上下文的本地摘要作为短期键。不能为了复用缓存而删除所有 query 后认定它们是同一授权资源。

## 6 Range 探测与测速指标

### 6.1 请求规格

```http
GET /原始媒体路径?原始查询字符串 HTTP/1.1
Host: 候选主机
Range: bytes=0-131071
Accept-Encoding: identity
```

128 KiB 对应 `0-131071`，256 KiB 对应 `0-262143`，1 MiB 对应 `0-1048575`。范围末尾为包含式边界。

测速请求使用经过筛选的必要头字段。Referer、User-Agent 等是否必需通过兼容性实验确定；不将完整 Cookie 或 Authorization 无条件复制到所有候选。关闭自动重定向，或只允许经验证的同类目标；否则候选 A 返回 302 到候选 B 会污染 A 的分数。

HTTP 允许服务端忽略 Range。`206`、`Content-Range` 和实际返回长度需共同验证；`200` 不能仅凭状态成功就被计入固定 Range 排名。`416` 应先检查对象长度和区间，而非直接认定节点故障。依据：[RFC 9110 Range Requests](https://www.rfc-editor.org/rfc/rfc9110.html#name-range-requests)。

### 6.2 有效采样条件

一个可用于同轮排名的样本须满足：无请求错误，返回符合预期的部分内容，区间与请求吻合，实际二进制字节数匹配，且未返回 HTML/JSON 错误页面。对象不足目标长度时，采用所有候选一致的较短区间另起一轮；不将短样本与完整大样本混排。

初版在回调收到完整响应后，使用二进制数据的实际 `byteLength`。超时没有可靠完整数据时，记为超时或未完成，不把期望的 Range 字节数当成已收到字节数。

### 6.3 指标定义

```text
elapsedMs = completedAt - startedAt
effectiveMbps = receivedBytes × 8 / (elapsedMs / 1000) / 1,000,000
effectiveMiBps = receivedBytes / 1,048,576 / (elapsedMs / 1000)
```

例：256 KiB 在 80 ms 完成，等效下载速率约 26.21 Mbps。128 KiB 在 45 ms 完成，约 23.30 Mbps。这些均为计算示例。

`effectiveMbps` 包含解析、建连、TLS、首字节等待和传输所造成的整体耗时；它不是纯粹的链路持续带宽。更大的样本可以降低固定开销占比，但仍需记录连接复用、缓存冷热和并发竞争影响。没有独立 TTFB 数据时，指标中不制造一个推测值。

### 6.4 测量干扰

高并发可能让所有节点共享用户接入带宽，测得的是竞争下的表现。粗筛允许较高并发快速淘汰；确认阶段默认串行，或在验证后使用很低并发。已在播放时，应降低并发和预算，避免测速本身制造卡顿。

重复测试同一 Range 会改变缓存与连接状态。记录采样次序，对相近候选采用轮换顺序或可比区间复测。单次粗筛未完成的节点只能被本轮跳过，不能由此断言它在长连接传输中一定更差。

## 7 选择算法

### 7.1 两种模式

**快速选择**是默认入口。先在本地构造最多 20 个候选的短名单，再做实测；有仍有效的当前资源决策时直接复用，不重复跑整份名单。达到目标并确认后即可停止，不追求覆盖全部清单。

**完整探索**覆盖本轮快照中的全部合格候选，经过三阶段筛选建立当前网络的候选排行。若被时间、预算、网络变化或用户停止中断，则标记为部分探索，并记录覆盖率，不能更新“已完成全量探索时间”。

### 7.1.1 预筛名单与扩展顺序

候选总数和并发数是两个独立参数。Surge 的 20 是每次脚本运行的在途 `$httpClient` 请求上限，并不要求全量数据库只能存 20 个主机。本项目另设默认短名单上限 20，以减少测速总请求数、流量和等待；日常并发仍可为 4 或 8。

| 来源 | 名额 | 选择规则 |
| --- | --- | --- |
| 当前资源原生 CDN | 1 | 必须保留为对照，不因地区推荐被挤出 |
| 本机当前网络历史 | 最多 5 | 当前资源历史赢家优先，其余按有效确认成绩 |
| 出口国家推荐 | 最多 10 | 冷启动按版本化推荐表顺序，后续可用本地实测重排 |
| 短名单外探索 | 最多 4 | 来自全域清单中未入围的节点；按轮换游标和 pool 多样性选取 |

这里的 20 是各来源名额的合计上限。候选经适配兼容性校验和当前资源冷却过滤后按 hostname 去重；同一节点出现多次只测一次，空缺不强制补满。没有历史的新加坡冷启动通常最多 15 个，已有历史时最多 20 个。用户指定的优先节点占用历史候选名额，不能绕开安全校验或偷偷增加上限。

探索名额只在探索触发且预算允许时启用；多数日常任务省略该部分。预算调度器可在测试全部短名单前结束，尤其蜂窝模式不保证 20 个都测试。未知或无推荐表的国家不会因为缺少地区节点就默认全扫。

预筛只读取清单和缓存，不为 299 个节点额外发送 DNS、HEAD 或 ping 请求。“先轻探测所有节点”仍属于扫描，不能当成零成本预筛。

短名单没有找到足够快的可用节点时，先检查原生样本与网络是否有效；有效且有预算时，再从全域清单选不重复的最多 20 个追加候选。按该流程逐批扩展，预算到达即停止。冷启动、网络变化和缓存过期默认触发小名单重选，不自动升级为完整扫描；完整探索由用户显式启动，或在用户启用该策略后于合适的 Wi-Fi 环境运行。

若首轮已有可播放但未达到高余量目标的节点，应先复用并记录待探索状态，不强迫用户等待找出更高分节点。首轮使用 128 KiB 的目标有效载荷仅约 1.875～2.5 MiB，之后的复筛、确认和在途误差另计。

### 7.2 三阶段参数

以下是实验起点，需要在目标设备实测后固化。表中 timeout 是单请求参数，阶段另有预算和总截止时间。

| 阶段 | 候选 | 单次 Range | 单请求超时 | 默认并发 | 输出 |
| --- | --- | --- | --- | --- | --- |
| 粗筛 | 短名单；完整探索时为全量 | 128 KiB，可选 256 KiB | 初始 0.8 秒 | 快速 Wi-Fi 4，完整 Wi-Fi 8，硬上限 20 | 快速模式 Top 3，完整模式 Top 20 |
| 复筛 | 粗筛入围 | 1 MiB | 1.5 秒 | 4 | 快速模式 Top 1，完整模式 Top 5 |
| 确认 | 复筛入围 | 快速模式 1 MiB，完整模式 4～8 MiB | 3 秒 | 1 | 赢家及备选；快速模式只确认赢家 |

蜂窝快速模式默认并发 2，自动全量探索关闭。原方案的 20 worker 作为可配置上限保留，不将 API 上限直接当作所有网络的默认最佳值。样本成功数不足时不填入虚构的 Top 20 或 Top 5；原生 CDN 可用时仍可继续播放。

在默认 `$httpClient` 适配器中，“4 MiB 或 3 秒”表示请求指定 Range 并设置超时；只有完整完成的响应进入正式吞吐排名。它不等价于在 3 秒时拿到可靠的部分下载统计。流式进度适配器须另行验证。

### 7.3 滚动调度

快速模式在预筛短名单内按当前资源赢家、原生 CDN、网络历史、地区推荐和探索节点调度。完整探索按历史 Top 20、地区推荐、其他近期成功节点及未充分探索节点调度，并穿插未测节点，防止历史顺序长期饿死新候选。

每个请求使用独立的 `startedAt`。例如 A 在全局第 0 ms 启动、300 ms 完成；B 在全局第 250 ms 启动、350 ms 完成，B 的实际耗时为 100 ms，应优于 A。按全局完成时刻取前 K 名会产生系统性偏差。

下面是调度伪代码，不是可直接导入 Surge 的脚本：

```text
while 存在未测节点 or active > 0:
    while 未停止派发 and active < concurrency and 允许启动下一个请求:
        从候选队列取节点
        按本阶段测量结果计算该请求 timeout
        预留该请求的预算
        active += 1
        发起真实 HTTP 探测

    收到真实回调时:
        active -= 1
        记录完整响应字节或不可观测流量状态
        校验样本并更新本阶段 Top K
        检查任务 token、网络代次和停止条件
        若满足停止条件，stopScheduling = true
        否则立即填补空闲 worker

等待在途请求真实结束，或由已验证适配器取消
一次性提交仍属于当前任务和网络的结果
结束独立任务
```

若使用 `Promise.race` 实现逻辑超时，被淘汰的底层 HTTP 请求仍然占用并发名额。必须在其真实回调到达后才减 `active`，否则会超过平台并发限制。

### 7.4 动态淘汰线

在同一阶段积累足够有效结果后，采用以下启发式决定后续新请求的 timeout：

```text
cutoffMs = clamp(alpha × kthBestElapsedMs, minTimeoutMs, maxTimeoutMs)
alpha = 2.5
粗筛参考：minTimeoutMs = 300，maxTimeoutMs = 800
```

例如同阶段第 10 名为 120 ms，下一批新请求可使用约 300 ms 的超时。样本不足时使用初始上限；成功率过低时放宽至一个保守的救援轮，例如 1.5 秒，并优先检查原生节点是否也变慢。

不同 Range 大小的阶段分别维护阈值。早期冠军不能直接将所有后续探测压缩到极短窗口。该方法偏向短采样响应快的节点，完整探索也可能错过建连慢但长传输快的节点；应保留少量宽松探测用于纠偏。

对在途请求，动态淘汰线只影响结果是否值得进一步确认，不修改已发出的 timeout，也不声称已经省下剩余流量。

### 7.5 足够快判定

快速模式使用如下初始目标：

```text
已知可靠视频码率：targetMbps = 4 × bitrateMbps
未知视频码率：targetMbps = configuredTargetMbps，默认参考 80
```

4K 不对应固定码率；若请求层无法可靠取得码率，应使用配置值，不按清晰度名称伪造码率。80 Mbps 只是可调整的体验目标，不是所有视频的最低要求。

只有确认阶段的有效样本才能触发足够快早停。快速模式以入围赢家的 1 MiB 复筛样本加一次 1 MiB 确认样本取较低结果，作为有限窗口下的可用速度判断，不标为持续带宽保证；完整探索使用 4～8 MiB 确认，需要早停时补做一次可比样本。所有复测额外流量计入预算。粗筛的高速结果仅允许提前进入确认阶段，不能直接被称为稳定带宽。

快速模式达到目标后，停止新增探测并处理完在途请求。完整探索默认继续覆盖候选；用户选择省流优先而允许早停时，结果必须标明部分覆盖。

### 7.6 切换迟滞与随机探索

当前节点仍可用时，候选至少达到当前确认分数的 1.25 倍，并满足 60 秒最小驻留时间，才因性能提升切换；这些为初始调参值。明确失败可绕过性能迟滞，进入降级流程。

预算允许时，约 10% 的新资源选择任务启用短名单中的探索名额，默认 2 个、最多 4 个，并计入 20 个候选总上限；用户手动扩展探索可使用独立批次。探索使用轮换游标与随机顺序结合，避免反复抽到同一组节点。原对话提出的额外 10～20 个随机节点不再作为日常默认参数。

## 8 缓存与持久化

### 8.1 缓存分层

| 层级 | 内容 | 初始有效期 | 失效条件 |
| --- | --- | --- | --- |
| 网络候选历史 | Top 节点、成功率、最近确认结果 | 12～24 小时 | 网络或出口上下文变化、清单变更 |
| 当前资源决策 | 视频或音频资源赢家、备选 | 10 分钟，上限可调至 20 分钟 | 签名到期、资源变化、错误或网络变化 |
| 样本上下文 | 真实 URL、必要头、采集时间 | 最长 2 分钟且不超过已知签名有效期 | 超龄、签名到期、网络变化 |
| 失败冷却 | 当前资源或主机失败记录 | 由失败类型决定 | 冷却结束后允许受控复测 |
| 运行租约 | 当前任务身份和截止时间 | 单任务截止时间加清理余量 | 任务结束、租约过期 |

保存历史性能不等于保存长期可用的签名链接。对于无法解析有效期的 URL，短样本 TTL 仅降低风险；若原生请求也拒绝访问，暂停该样本测试并等待新播放请求。

### 8.2 网络上下文

网络键基于连接类型、可用的 Wi-Fi 标识或蜂窝运营商字段，以及出口策略配置代次计算本地摘要。BSSID 在 Mesh 漫游时可能变化，默认不必每次都创建全新画像；可将其作为变化信号。字段缺失时使用保守的短期未知网络画像，不让所有未知网络永久共享同一个赢家。

相同 SSID 可能出现在不同地点，相同代理组名称也可能切到不同出口。若无法获得实际代理出口身份，应提供用户可更新的 `routeRevision`，缩短缓存，并在观察到性能突变时重测。

### 8.3 数据结构草案

以下为 JSON 字段示意，其中 `null` 表示尚无结果，示例域名不是可用节点：

```json
{
  "schemaVersion": 1,
  "candidateRevision": "list-v1",
  "networkKey": "local-network-digest",
  "networkGeneration": 1,
  "routeRevision": "direct-v1",
  "lastFullScanAt": null,
  "lastAttemptAt": null,
  "coverage": { "eligible": 300, "started": 0, "valid": 0 },
  "ranking": [],
  "resourceDecisions": {},
  "cooldowns": {},
  "lease": null
}
```

每个 `ranking` 条目至少包含 hostname、资源族、确认分数、样本数、成功率、测量时间和测量模式。每个资源决策包含资源键、winner、已确认备选列表、过期时间、选择原因和所属网络代次。`backupVersion:1` 表示备选已经过复筛与确认；未确认或确认失败的节点不得进入播放回退链。`invalidHosts` 记录复测发现失效的已有选择，即使没有找到替代节点也停止继续改写到该节点。小样本分数与确认分数不得混为同一字段。

样本 URL 与必要头独立存储，避免在排行榜导出时泄露签名。限制画像数量和资源决策数量，采用 LRU 清理。持久化失败不得中断播放，损坏 JSON 需回落到空状态并在面板报告。

### 8.4 并发写入

简单 key-value 读写不是原子 compare-and-swap。多个请求脚本通过“读空锁再写锁”不能保证唯一任务。设计上由一个调度入口负责创建任务，请求热路径写节流后的样本、待测提示和独立请求关联槽。请求关联使用 256 个有界槽，按请求 ID 摘要定位，每条记录有效 5 分钟；读取时同时核对完整 ID、资源键和过期时间。槽碰撞、缺失、存储失败或超龄只导致跳过该响应观察，不根据当前路由猜测归属。

任务携带 `runId`、`networkGeneration`、`resourceKey`、`candidateRevision` 和租约到期时间。提交前重新验证身份；过期任务的回调不得覆盖新网络或新任务结果。唯一写入者、手动与自动入口互斥以及租约恢复机制都需做并发实测，不能仅靠存储中存在一个 lock 字段就视为完成。

## 9 流量与时间预算

### 9.1 理想有效载荷计算

统一采用 KiB 和 MiB，避免将二进制单位与十进制 MB 混写。在每个请求严格遵守 Range、没有重试的前提下：

| 方案 | 计算 | 目标有效载荷 |
| --- | --- | --- |
| 全节点大样本 | 300 × 8 MiB | 2400 MiB，约 2.34 GiB |
| 快速模式目标开销 | 15～20 × 0.125 MiB + 3 × 1 MiB + 1 × 1 MiB | 5.875～6.5 MiB |
| 128 KiB 粗筛 | 300 × 0.125 MiB | 37.5 MiB |
| 256 KiB 粗筛 | 300 × 0.25 MiB | 75 MiB |
| 20 节点复筛 | 20 × 1 MiB | 20 MiB |
| 5 节点确认 | 5 × 4～8 MiB | 20～40 MiB |
| 128 KiB 三阶段合计 | 37.5 + 20 + 20～40 | 77.5～97.5 MiB |
| 256 KiB 三阶段合计 | 75 + 20 + 20～40 | 115～135 MiB |

这些值不包含额外确认轮、原生对照复测、协议开销、重传和服务器忽略 Range 的流量，因此不能直接宣传为“严格最大耗流量”。早停可减少尚未派发的下载，但不自动取消在途数据。

### 9.2 预算策略

初始策略建议：手动 Wi-Fi 完整探索目标预算 100 MiB；日常快速选择目标预算 12 MiB；蜂窝快速选择目标预算 4 MiB，并禁用自动完整探索。蜂窝调度须先预留复筛和确认的预算，再决定测试几个候选以及复筛几个入围节点；4 MiB 不足以照搬 Wi-Fi 的完整快速流程。预算不足以完成确认时，使用原生请求或仍有效的已确认决策，不能把粗筛结果升级为已确认结果。

每次派发前预留目标 Range 字节，避免多个 worker 同时认为剩余预算充足。正常完成后以实际字节结算；超时且无法得知已下载量时，保留保守预留并标记“实际用量不可精确观测”。

`$httpClient` 完成回调模式不能在收到超大 `200` 响应头的一瞬间可靠取消下载。发现忽略 Range 的节点后应退出后续探测并进入冷却；若产品要求严格流量硬上限，必须实现并验证可在响应头或流式读取阶段中止的适配器，否则不能开启宣称有硬上限的模式。

### 9.3 时间预算

以 300 个候选、每个最长 0.8 秒、20 并发估算，粗筛最坏理想调度耗时约 `ceil(300/20) × 0.8 = 12 秒`；8 并发约为 30.4 秒。还需加入复筛、串行确认及运行开销。因此完整探索不能被包装成必定在 1～2 秒内完成。

独立任务可先采用 60 秒应用级截止时间、65 秒脚本超时作为实验参数，并检查目标 Surge 版本是否支持且运行稳定。接近截止时间时停止新增任务，给已发请求留下收尾时间。若无法完成，保存部分覆盖结果；后续用新鲜样本继续探索，跨视频样本只更新历史先验，不能拼成一次同资源完整排名。

## 10 失败处理与回退

### 10.1 错误分类

| 错误或现象 | 判断范围 | 动作 |
| --- | --- | --- |
| 403 | 可能为签名、IP、Host 或权限不匹配 | 当前资源降级；对照原生 URL，不立刻全局封禁主机 |
| 404 | 可能为路径不兼容或资源不存在 | 记录资源与主机组合失败 |
| 416 | 区间超出对象长度 | 调整统一探测区间或跳过小对象 |
| 429 | 请求过于频繁 | 尊重可用的 Retry-After，退避并减少并发 |
| 5xx | 服务端临时异常 | 短期冷却，允许后续复测 |
| DNS/TLS/连接错误 | 地址或传输路径不可用 | 保留证书校验，回退原生路径 |
| 探测超时 | 本轮未取得完整样本 | 不计为完整速度，不永久删除节点 |
| 全部候选与原生都失败 | 样本或网络可能有问题 | 停止扩大扫描，等待新样本 |
| 当前赢家仅变慢 | 性能下降 | 受预算和迟滞约束进行快速复测 |

### 10.2 实际播放观察的能力边界

响应脚本在不缓冲响应体时可读取状态和头，适合记录可见 HTTP 失败；请求 ID 可用于请求与响应关联。见 [响应脚本说明](https://manual.nssurge.com/scripting/http-response.html)。

没有响应头的超时、播放器停滞、缓冲见底或解码失败，并不会自动变成上述脚本可见的事件。真实播放容灾需要额外的受支持遥测，或者采用有限探测来重新验证。首期明确保证的是“探测失败和可观察 HTTP 失败后的后续请求降级”，不承诺对所有卡顿即时自动恢复。

### 10.3 回退顺序

当前资源已确认的次优节点优先；只有完成复筛和确认且没有后续失败的节点可以成为备选。没有可用备选时恢复该请求的原始 URL 和原始相关头。针对每个资源及决策身份记录改写来源与次数，禁止 A、B 节点之间无限循环；重新测速产生新决策后，旧决策的切换次数不封锁新决策。

响应观察只能更新后续决策，不能把已经收到的 403 无代价地重新发送成另一个请求。当前失败请求通常依赖 App 自身重试；若以后实现代理式重试，须单独设计请求幂等性、Range 一致性和重复流量预算。

请求入口和任务入口共用可用性判定：网络、TTL、禁用状态、资源失败、主机冷却、测速冷却及决策切换限制均参与判断。整条缓存回退链失效时，手动快速选择可立即重新发现；自动选择须满足默认 300 秒的重试退避，按“网络键 × 资源键”记录上次尝试。

失败缓存按请求发出时的网络键隔离，包含出口配置版本。切网后的迟到响应只写回旧网络；不同网络的主机冷却、资源失败和切换计数互不影响。响应归属只使用请求关联记录，测速请求即使已经去掉内部标记也不会计入播放故障。

MVP 可在一次明确的当前资源 403/404 后立即退回原生资源；短期多资源连续失败才将主机置于更广泛冷却。不得因为一个授权 URL 过期就把全清单都记为坏节点。

### 11.3 集成约束

MITM 只覆盖经过验证的媒体来源主机，不能使用任意域名通配。证书配置和目标协议是否进入 HTTP 引擎需要实际检查，不能仅因安装了模块就认定所有 App 请求可见。QUIC、证书固定或特殊网络路径应在兼容性实验中处理，未支持时明确直通。

与 Biliverse Redirect 或其他媒体改写规则避免重复匹配。先备份配置，停用重叠的 Redirect 部分，再验证本项目的规则顺序；其他模块是否共存以匹配范围为准，不能笼统保证完全兼容。

测速流量与真实播放必须走一致出口。若候选域名触发不同 Surge 规则，需在任务中记录实际策略差异，或者统一到用户选择的策略。不能拿 DIRECT 测速结果去指导另一个代理出口的播放。

还需验证脚本发起的探测是否会再次进入本项目的改写逻辑。优先依赖已核实的运行时隔离；如果引入内部标识，必须防止污染外发请求和递归触发，不能通过随意添加 query 参数破坏签名。

## 12 可观测性与操作界面

面板至少显示当前网络类型、当前资源是否有已确认选择、winner、备选数量、样本时间、任务阶段和停止原因。展示“本轮有效样本数 / 已启动节点数 / 合格候选总数”，区分部分探索与完整探索。

测速流量应区分完整回调可见字节、保守预留量和不可观测误差，不能显示一个看似精确的总用量掩盖超时数据缺失。支持重新探索、快速选择、停止派发、清空当前网络缓存及关闭改写。

结构化日志事件包括：`sample_captured`、`probe_started`、`probe_completed`、`probe_rejected`、`selection_confirmed`、`scheduling_stopped`、`cache_invalidated`、`fallback_selected`。每条事件包含任务标识、网络代次、阶段、节点、耗时、字节数及错误分类。

默认日志不记录完整签名 URL、Cookie、Authorization、SSID 或 BSSID。面板可显示用户可理解的本地网络别名，导出诊断时使用脱敏标识。默认不上传遥测。

## 13 测试与验收

### 13.1 运行时能力实验

| 实验 | 必须得到的证据 | 未通过时的处理 |
| --- | --- | --- |
| 媒体请求识别 | App 的目标请求能稳定命中，非媒体请求不命中 | 缩小支持范围 |
| Host 与 URL 改写 | 实际目标、Host、路径和 query 均正确 | 暂停自动改写 |
| Range 行为 | 验证 206、长度、忽略 Range 和小对象情况 | 限制候选与预算承诺 |
| timeout 精度 | 0.3、0.8、1.5 秒等参数在目标版本中的真实表现 | 调整到已支持的精度 |
| 并发上限 | 记录真实在途数，逻辑淘汰不会提前释放名额 | 禁用动态淘汰或降低并发 |
| 独立任务生命周期 | 请求脚本已结束时，独立任务仍能完成并写结果 | 仅开放手动模式 |
| 脚本递归 | 探测不会被二次改写或重复采样 | 修正隔离机制 |
| 出口一致性 | 探测与播放策略一致，变化时缓存失效 | 按策略隔离结果 |
| 网络切换 | 旧回调不会污染新网络选择 | 禁止跨切换提交 |
| 任务互斥 | 音视频并发、手动与自动触发不产生重叠扫描 | 保留唯一手动入口 |

### 13.2 核心逻辑测试

使用模拟时钟与模拟请求结果测试下列场景，不必用真实视频反复消耗流量：

- URL query 中重复参数、百分号编码、加号、空值和非标准端口得到保留或被明确拒绝。
- 大小写不同的 Host 不会产生冲突，真实播放 Range 不被探测 Range 覆盖。
- 滚动队列中后启动但耗时更短的节点可以进入 Top K。
- 假超时不会降低真实在途数，早停后不再派发新请求。
- 206 错误区间、短响应、200 完整对象、HTML 错误体和 302 不进入有效速度排名。
- 原生样本也失效时停止扩散失败，单资源 403 不污染全网历史。
- 清单为 0、1、19、20、21 和 300 以上节点时都可正常结束。
- 数据损坏、存储写入失败、过期租约、网络代次变化和乱序回调能安全降级。
- 未确认的小样本成绩不能触发稳定高速早停。
- 预算恰好耗尽时停止派发，部分探索不更新完整探索时间。
- 地区表、历史表和原生 CDN 大量重复时正确去重，短名单不超过 20，原生节点不被挤出。
- SG 冷启动使用已固定版本的 10 节点推荐表，武汉候选不会因机房不在新加坡被过滤。
- 已测成功且有效的当前资源请求不重复测速；地区识别失败或全量探索未启用时不自动扫描所有节点。

### 13.3 实机对照矩阵

至少覆盖家庭 Wi-Fi、另一条 Wi-Fi 和蜂窝网络；不同画质、不同视频热度、视频与音频分开记录；新鲜样本与过期样本、DIRECT 与用户实际代理策略分组比较。平台版本记录 iOS、Surge 和 Bilibili App 的实际版本。

对照组包括原生 CDN、固定手动 CDN 和自适应选择。每组使用相同视频、清晰度与操作序列，轮换执行顺序，减少时段变化与缓存预热偏差。建议至少完成 10 组配对播放会话，报告中位数、P95 和样本数量，不用一张速度截图宣告完成。

记录首帧等待、5 分钟播放中的缓冲次数与总时长、拖动后的恢复时间、失败状态码、模块增加的请求决策耗时、额外流量及异常退出。播放器指标若无法自动采集，采用明确的人工计时步骤，不编造自动化遥测能力。

### 13.4 发布门槛

1. 关闭模块后恢复原生行为，未知资源始终直通。
2. 热路径没有网络测速等待；以缓存命中的原生对照测量附加延迟，初始目标为 P95 不超过 100 ms，包含脚本启动和排队开销。
3. 真实并发受限，任务可结束，过期回调不覆盖新状态。
4. 采样有效性、签名保持和资源一致性检查全部通过。
5. 默认蜂窝不会自动启动完整探索，预算报告不冒充严格硬上限。
6. 至少在一个可复现的原生 CDN 慢速场景中改善缓冲或拖动体验，同时未引入新的播放失败。
7. 若自动任务和真实请求失败观察尚未验证，发布说明明确标为手动探索版本，不宣称完整自动容灾。

## 16 排障附录

网页端可观察缓冲长度、下载速率、视频与音频请求、已解码帧以及全屏与窗口模式差异。缓冲持续降低且媒体请求不返回，支持优先调查网络；缓冲充足、解码或画面输出异常，则应比较播放器、编码格式和浏览器。原对话引用的某个 Chrome 问题报告只能作为排查线索，不能直接认定为用户设备根因。

手机端使用同一视频和画质，分别比较 Wi-Fi App、蜂窝 App 与 Wi-Fi 网页播放。不同网络可能影响路由和 CDN 分配，不同客户端也可能请求不同资源，因而结果用于缩小范围，不是一次对照就能排除所有其他因素。

更换 DNS 可能改变同一 hostname 的解析地址，但不等于把播放接口选定的 CDN hostname 改成另一个。代理改变出口路径，也可能改变授权和区域上下文；应与 CDN 选择分开验证。不要仅通过批量屏蔽媒体域名强迫回退，避免可用资源被一并阻断。

### 18.2 实现中确定的取舍

1. 脚本引擎：请求与响应脚本使用 JSC 以降低启动延迟；面板与测速任务使用 WebView，避免长任务占用 JSC 仅有的 2 个并行会话。
2. 自动触发：`MODE=adaptive` 时，请求脚本在采集到无可用决策的资源且满足重试退避后调用 `$httpAPI` 的 `POST /v1/scripting/cron/evaluate` 运行 `BiliCDN-Runner`，30 秒内最多一次；另有每 15 分钟一次的 cron 后备。手动模式下两者都立即退出。触发后的会话能否独立完成，属于 M0 生命周期实验。
3. 防递归：测速请求携带 `X-BCP-Probe` 头。请求脚本若看到该头，会删除它并直通，不改写、不采样；响应脚本同时根据请求 ID 关联记录忽略带标记和已去标记的探测。可通过 `probeMarker:false` 关闭。
4. 原生对照：赢家成绩未达到原生节点确认成绩的 1.25 倍时保留原生（原因 `native-competitive`），被替下的赢家保留为已确认备选。只有确认成绩参与比较：原生的复筛成绩足以构成竞争时，快速模式会给原生补做一次确认；原生确认失败则不再参与。
5. 确认区间：对象足够长时，确认读取紧接复筛区间之后的同等大小区间，避免命中刚缓存的字节。快速与完整模式的确认成绩都取复筛与确认中的较低值，决策另记 `scoreMode`。
6. 预算粒度：目标预算按资源计算（快速 12 MiB、蜂窝 4 MiB、完整 100 MiB），一次任务最多处理 2 个资源，通常是同一次播放的视频与音频。快速模式先预留复筛与确认的预算，再决定粗筛数量；蜂窝时复筛入围数可降为 1。
7. 救援轮：粗筛没有有效结果，或有效率低于 20% 时，以 1.5 秒超时重测最多 4 个超时节点，原生优先，每阶段一次。
8. 响应归属：以 `$request.id` 对应的请求发出记录为准，不查询当前路由来推断。响应暴露原始 URL 或改写后的 URL 都不影响已记录的目标；没有可靠关联时跳过。旧原生请求晚返回不会处罚新 winner，旧网络响应不会处罚新网络。切换计数按资源与决策身份区分，同一主机的并行失败只算一次，每次决策上限 3 次。
9. 网络画像：Wi-Fi 以 SSID、蜂窝以运营商为身份，经本机随机盐生成摘要，BSSID 不参与。拿不到身份时，画像绑定当前网络代次，`network-changed` 事件后即失效。
10. 冷却：全部失败记录按网络键和出口配置隔离。403/404 只冷却“资源 × 主机”；30 分钟内同一主机在 3 个不同资源上失败，才冷却该主机 30 分钟。5xx、429（尊重 Retry-After）、DNS/TLS/连接错误、重定向和忽略 Range 按类型设定有期限的主机冷却，到期后允许复测；超时不增加全局主机冷却，但当前决策中复测失败的节点会被标记不可用。自动完整探索每次尝试后（包括部分探索）至少间隔 `fullRetrySeconds`（默认 1 小时）。
11. 持久化：按写入者角色拆分键（samples、decisions、failures、state、meta、control、trigger、lease、lastRun）以降低竞争，另有 256 个请求关联槽；同角色的并行会话仍可能发生非原子读改写，不能据此声称已实现事务。租约只是尽力而为，每次提交前重新校验租约、网络代次与网络键。
12. 候选清单：从上游固定提交导入并重新校验；上游许可证只允许个人非商业使用，见 [data/NOTICE.md](../data/NOTICE.md)。

### 18.4 审查修复与升级行为

v0.3.1 修复以下五项问题，并同步更新源码与可导入脚本：

| 问题 | 修复行为 | 回归场景 |
| --- | --- | --- |
| 迟到响应误归属 | 请求 ID 关联实际目标和原网络，不再推断 | 原生请求在选出 winner 后返回 403；旧 winner 请求在新决策后返回；缺失与过期 ID |
| 确认失败节点成为备选 | 快速与完整模式只输出已确认备选；复测失败使旧决策失效 | 复筛很快、确认超时的节点不参与回退；无替代节点时恢复原生 |
| 失败决策阻止重测 | 请求和任务入口共用可用性判断，自动退避按网络与资源记录 | 手动恢复耗尽的回退链；自动模式退避后恢复；旧切换计数不封锁新决策 |
| 失败跨网络传播 | `failures` 升为 `v:2`，按 `networks[networkKey]` 保存 | Wi-Fi 切蜂窝、出口版本变化、旧响应在切换后到达 |
| 禁用节点被重新引入 | 禁用状态覆盖地区、历史、优先项与已有决策 | 禁用武汉推荐第一项后，快速和完整模式都不探测或选中它 |

升级时旧版 `v:1` 失败缓存因没有网络身份而被忽略，首次新失败写入 `v:2`。旧决策没有 `backupVersion:1` 的备选列表被丢弃；原有已确认 winner 在其余检查通过时仍可使用。无需用户手动清空缓存。

关联记录只存请求 ID 和本地决策元数据，不包含签名 URL。`clear-all` 会清除关联槽；槽数量有上限，碰撞与 5 分钟有效期可能减少故障观察覆盖率，但不会把响应归给其他请求。请求入口增加了一次有界记录写入，附加延迟仍需按 M0 在实机测量。


### 18.5 手机导入参数声明修复

实机导入发现模块头中的 `PROBE_POLICY:` 被拒绝，报错为 `Malformed argument declaration in module header`。无默认值的参数现声明为 `PROBE_POLICY`，省略冒号；运行时仍以空策略表示遵循现有路由规则，不强制指定出口。该写法对应 [Surge 模块参数说明](https://manual.nssurge.com/profile/module.html)。此次仅修复模块配置和构建校验，远程脚本继续固定为 v0.3.1 的已验证提交。

同类检查覆盖本地与远程模块的全部 9 个参数、占位符声明与引用、6 条脚本声明、2 个面板引用、引号和逗号分隔、HTTP 匹配正则、cron 与 event 必填项，以及远程脚本 HTTPS 路径。没有发现其他现存的同类声明错误。原先 `build --check` 会跳过远程模块，现将它纳入默认构建和逐字一致性检查，固定基地址保存在 `tools/remote-module.json`。

新增 8 项回归测试，包括拒绝截图中的空冒号声明、默认和显式测速策略的实际请求选项、远程模块与本地模块的一致性，以及损坏远程模块后构建检查必须失败。`tools/validate-module.cjs` 是本项目所用配置结构的静态检查器，不能替代 Surge 原生解析器和实机验收。


### 18.6 手机入口和可观测性修正

v0.3.2 针对实机反馈补充以下能力。用户后续截图确认媒体请求为 HTTPS Akamai、请求已完成且有传输字节，URL 符合旧版匹配范围；早先 0 KB/s 的播放异常已自行恢复。Bilibili 的 DIRECT 策略只决定出口，不会阻止 CDN hostname 改写。当前证据尚不能确认“模块已勾选但脚本和面板未显示”的最终原因。

1. `DEBUG` 同时绑定原生脚本声明中的 `debug`，使内部 console 日志能够出现在请求 Notes；每次匹配输出脱敏 `router_matched` 标记，便于区分未匹配、日志不可见和样本节流。
2. 增加只读 `BiliCDN-Diagnostics` 入口，输出代码版本、Surge 版本、网络和样本状态。generic 控制脚本支持编辑器和快捷指令手动触发，并通过日志和本机通知显示结果；定期刷新仍不测速。
3. 提供独立的无参数诊断模块，固定手动模式和调试开关，包含一个无需运行脚本的静态加载标记。它用于排除参数替换和区分配置／显示问题，并不保证绕过 Surge 的面板功能授权。诊断版和普通版必须二选一启用。
4. 补充公开案例中出现的 HTTP 80 Akamai 请求及限定主机的 `force-http-engine-hosts`。保持原协议，不把 HTTPS 降级；资源键增加协议和端口，旧版本决策自然失效并重新采样。该兼容补充不是对用户这条 HTTPS 请求的根因解释。
5. 模拟测试覆盖截图同类 HTTPS URL、HTTP `:80`、不支持的协议端口组合、无面板手动入口、只读诊断、原生 debug 绑定和静态诊断模块。iOS 模块的实际应用与面板显示仍需手机确认。

### 18.7 区分主配置编辑列表与模块脚本运行

实机反馈确认：诊断模块的三个面板已经显示，但 `Home → Modify → Scripting` 仍为空。不能据此判断模块脚本未加载，也不能把“必须能在此列表找到 BiliCDN-Router”作为验收条件。Surge 官方说明模块设置叠加于主配置之上、不通过主配置 UI 修改；其公开文档并未逐一规定每个 iOS 版本此页面的显示细节，因此不将“所有版本只显示用户自己写的脚本”作为绝对结论。区别是配置来源与编辑视图，不是脚本作者。

验证依据分为三层：面板卡片出现证明模块的面板声明生效；点击刷新后出现版本、网络、样本或具体错误，证明控制脚本执行；媒体请求 Notes 的 `router_matched`／样本存储更新才证明请求脚本命中。控制脚本已运行但显示暂无样本时，应继续检查媒体请求处理，不再反复排查模块是否导入。

远程 JS 属于外部资源，可从模块相关外部资源页面核对；需要完整配置脚本清单时使用只读 `GET /v1/scripting`，不以 Modify 编辑器列表替代。正常用户测试优先使用现有面板刷新入口，无需因编辑列表为空再次安装模块或复制脚本到主配置。

依据：[Surge 模块的 UI 编辑边界](https://manual.nssurge.com/profile/module.html)、[面板初始内容与运行后结果](https://manual.nssurge.com/tools/panel.html)、[配置脚本与外部资源查询](https://manual.nssurge.com/tools/http-api.html)。
